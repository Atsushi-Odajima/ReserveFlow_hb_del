# 予約枠エンジン仕様（BOOKING_ENGINE）

実装：`src/server/engine/`（DB に依存しない純粋関数）。空き枠一覧（`listSlots`）と確定時の再検証（`checkSlot`）は
**同じ関数** を使う。確定時は DB ロック取得後に最新データを読み直して `checkSlot` を再実行する。

## 1. 用語

| 用語 | 定義 |
|---|---|
| サービス時間 | `start` 〜 `start + duration` |
| 占有時間（occupied） | `start - bufferBefore` 〜 `start + duration + bufferAfter` |
| セッション | 同一サービス・同一開始・同一スタッフで同時に受け付ける1回の実施単位。定員1のサービスは予約1件=1セッション |
| アロケーション | セッションがスタッフ/リソースを占有する記録（`allocations` テーブル） |
| 有効な予約 | 状態が `confirmed`（予約確定）/`checked_in`（来店・開始済み）/`completed`（完了）/`no_show`（無断欠席） |

例：60分、準備15分、片付け15分、10:00開始 → サービス 10:00-11:00、占有 **09:45-11:15**。
同じスタッフ（または同じ定員1リソース）に 10:30 開始の予約は入らない（占有 09:45-11:15 と重なるため）。
11:15 以降に準備15分のサービスなら 11:30 開始が最短。

## 2. 占有ルール（スタッフ/リソースへの適用）

1. **スタッフ**：占有時間の全体（準備＋サービス＋片付け）を占有する。準備・片付けもスタッフが行う前提。
2. **リソース**：占有時間の全体を占有する（部屋の準備・清掃を含む）。
3. **営業時間**：**サービス時間** が事業者の営業時間内に収まること。準備/片付けは営業時間外にはみ出してよい
   （開店前準備を許容するため）。ただし次の 4, 5 は占有時間全体で判定する。
4. **スタッフ勤務時間**：占有時間の全体がスタッフの勤務時間（休憩・休みを除く）に収まること。
   スタッフが「事業者の営業時間に従う」設定なら勤務時間＝営業時間。この場合、営業 10:00 開始・準備15分のサービスの
   最初の枠は 10:15 になる（勤務開始を 9:30 にすれば 10:00 から受付可）。
5. **リソース利用可能時間**：リソースに利用可能時間を設定した場合、占有時間の全体がその時間内に収まること。
   未設定なら時間制限なし（ブロック・休止のみ適用）。
6. **ブロック**：事業全体ブロックは全予約の占有時間と重なれば不可。スタッフ/リソースのブロックは該当スタッフ/リソースのみ。
7. **リソース同時利用数（quantity）**：占有時間内のどの時点でも、そのリソースを使うセッション数が quantity 未満であること
   （新しいセッションを加えて quantity 以下）。同一セッションへの相乗り（定員制）は数に含めない。
8. **スタッフ**：同時に1セッションのみ。重なる別セッションがあれば不可。

## 3. 空き枠生成アルゴリズム（slots モード）

入力：事業者設定、営業時間（曜日別・複数区間）、日付例外、ブロック、スタッフ（勤務時間・対応サービス）、
リソース、サービス、既存アロケーション、既存セッション、現在時刻 `now`。

1. 対象期間の各「事業者ローカル日付」について、営業区間を求める（§5 の優先順位）。
2. 営業区間の開始から **壁時計（ローカル時刻）** で `slotInterval` 分刻みの候補開始時刻を作る
   （サービス個別の刻み > 事業者の刻み）。存在しないローカル時刻（DST 開始）は候補にしない。
   重複するローカル時刻（DST 終了）は早い方のみ（TIMEZONE_RULES.md）。
3. 各候補について `checkSlot` を実行：
   1. サービスが受付中・未アーカイブ・（公開ページでは）公開。
   2. 人数 1 以上・サービスの1予約最大人数以下。
   3. 公開予約：`start >= now + 最短受付時間`、かつ開始のローカル日付 `<= 今日 + 予約可能日数`。
   4. サービス時間が営業区間（隣接区間は連結済み）に完全に含まれる。
   5. 事業全体ブロックと占有時間が重ならない。
   6. 必要リソースそれぞれ：未アーカイブ、利用可能時間内、リソースブロックなし、同時利用数に空き。
   7. スタッフ必須サービス：候補スタッフ（指定 or おまかせ対象）ごとに、有効・受付可・未アーカイブ・対応サービス、
      勤務時間内、スタッフブロックなし、他セッションと重ならない。
   8. 定員制：同一サービス・同一開始・同一スタッフの既存セッションがあれば相乗り（残席 >= 人数）。
      なければ新セッション（実効定員 >= 人数）。
4. 1人でも条件を満たすスタッフがいれば枠を表示（おまかせ時）。

「カレンダーが空白だから予約可」という判定はどこにも存在しない。常に上記すべてを満たすこと。

### 実効定員
`min(サービス定員, 各必要リソースの人数上限(設定時), スタッフの最大同時人数(設定時))`

## 4. おまかせ割当ルール（AI 不使用・説明可能）

候補スタッフのうち **その枠で予約可能な人だけ** を対象に、次の順で1人を選ぶ：
1. 同じ開始時刻の同サービス既存セッション（相乗り可能）を担当しているスタッフ
2. その日（事業者ローカル日付）の有効予約件数が少ないスタッフ
3. スタッフの表示順
4. staffId（安定化のため）

アーカイブ済み・受付停止中・対応外のスタッフは対象外（テスト 14, 20）。

## 5. 営業時間の優先順位（詳細は DECISIONS.md D-004）
1. 事業者の日付例外「臨時休業/祝日休業（closed）」→ その日は終日休業（同日に特別営業があっても休業が勝つ）
2. 事業者の日付例外「特別営業/短縮営業（special_hours）」→ 通常の曜日営業時間を置き換える（定休日でも営業可）
3. 曜日ごとの通常営業時間（定休日は区間なし）
4. その上でブロック（事業/スタッフ/リソース）が時間帯を差し引く
スタッフの休み・半休は「スタッフのブロック」として登録する。

## 6. 開催枠（sessions モード＝繰り返し開催）
定員制の教室/ワークショップ向け。サービスを `sessions` モードにすると、空き枠は自由生成せず、
**開催回（session_occurrences）** から提示する。開催回は作成時点でスタッフ/リソースを占有（アロケーション）する。
公開表示条件：開催予定・受付中・最短受付/予約可能期間内・残席 >= 人数・事業者休業日でない・事業ブロックと重ならない。

## 7. 確定時の競合防止（予約競合モデル）

```
BEGIN (READ COMMITTED)
  SELECT pg_advisory_xact_lock(hashtext('rf:biz:' || business_id))   -- 事業者単位で確定処理を直列化
  冪等キー（idempotencyKey）で既存予約を検索 → あれば同じ予約を返す（再送/連打対策）
  最新の営業時間/例外/ブロック/スタッフ/リソース/アロケーションを読み直す
  checkSlot(...)  → 不可なら 409 SLOT_UNAVAILABLE（代替候補を返す）
  INSERT booking / allocations / status_history / manage_token / notifications / audit
COMMIT
```
- DB の防御層：`allocations` にスタッフの排他制約
  `EXCLUDE USING gist (target_id WITH =, occupied WITH &&, session_key WITH <>) WHERE (active AND kind='staff')`。
  アプリのバグがあってもスタッフの二重占有は DB が拒否する（23P01 → 409 に変換）。
- `bookings (business_id, idempotency_key)` のユニーク制約で同一送信の二重作成を拒否。
- ロックはトランザクション終了で自動解放（デッドロック・解放漏れなし）。

### 変更（リスケジュール）
同一トランザクションで：ロック → 新候補を検証（自分自身の占有は除外）→ 新予約作成（`rescheduled_from`）→
旧予約を `rescheduled`（変更済み）にしてアロケーション無効化 → 管理リンクを新予約へ付け替え。
検証失敗時はロールバックするため **旧予約はそのまま残る**（テスト 11）。

### キャンセル
予約行を `FOR UPDATE` → 状態遷移チェック → アロケーション無効化（枠が再開放）→ 未送信リマインドを取消 →
キャンセル通知 → 待機リストの一致候補を算出し管理側へ表示（自動確定しない）。

## 8. 管理側（手動予約・強制予約）
- 電話/店頭/DM 予約も同じ `checkSlot` を使う。最短受付時間と予約可能期間のみ免除（当日飛び込み対応）。
  それ以外（営業時間、勤務時間、ブロック、重複、定員）は公開予約と同じ。
- 「強制予約」（オーナーのみ・理由必須・監査記録）は営業時間/勤務時間/ブロック/刻みを免除できるが、
  **他予約とのスタッフ重複・リソース同時利用数・定員は免除しない**。すなわち二重予約はどの経路でも作れない。
- ブロック登録は既存予約をキャンセルしない。重なる既存予約を警告表示する。

## 9. 性能
- `EngineContext` がアロケーションを「スタッフ/リソース単位・開始時刻順」に索引化し、二分探索で重なりを判定。ブロック・同時刻の定員セッション・
  開催回の予約・スタッフ別当日件数も索引化。タイムゾーン変換（Luxon）はメモ化。
- 取得範囲は対象日付の前後2日（バッファ・深夜跨ぎを確実に含める）。
- 実測（20万予約データ）：公開ページ1か月分の空き枠 p95 約0.8秒、管理の空き検索7日 p95 約0.25秒（TEST_REPORT.md §4）。
