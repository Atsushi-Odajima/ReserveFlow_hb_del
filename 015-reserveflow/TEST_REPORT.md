## 4. 負荷・競合（参考値。販売上の保証値ではない）
データ：サービス100／スタッフ50／リソース100／顧客50,000／予約200,000（占有20万件）／通知500,000。1事業者に集中。
サーバー1プロセス（DB プール10）・同一マシンの PostgreSQL。各 API 40 回、同時 4。単位 ms。

| 競合シナリオ | 結果 |
|---|---|
| 同一枠へ 50 同時確定（管理 API） | 成功 1 / 409 49 / その他 0（合計 4.9 秒） |
| 別々の枠へ 100 同時確定（公開 API） | 成功 100 / 409 0 / その他 0（合計 6.5 秒、p50 3.4 秒、p95 6.2 秒） |

所見：
- 初回計測で「公開ページ 空き枠（1か月）」が **93 秒** かかる問題を発見 → エンジンの索引化と日時変換のメモ化で 0.7 秒に改善（DECISIONS D-027）。
  受付画面も顧客別集計の索引不足で 3.1 秒 → 0.06 秒に改善（002_perf.sql）。
- 確定処理は事業者単位で直列化するため、同一事業者への大量同時確定は待ち行列になる（100 同時で最後の応答まで約 6 秒）。
  小規模事業者の実際の同時予約数では問題にならない想定だが、対応件数として広告しない。
- 氏名の部分一致検索（全期間）は約 1 秒。期間を絞ると高速。
- 生データ：`tests/load/results/load-2026-09-30.json`。
